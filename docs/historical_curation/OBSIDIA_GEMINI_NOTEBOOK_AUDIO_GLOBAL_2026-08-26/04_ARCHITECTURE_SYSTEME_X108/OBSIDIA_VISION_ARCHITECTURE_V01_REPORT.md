0. VERDICT EXÉCUTIF

Obsidia n’est pas un agent monolithique, ni un simple routeur, ni un LLM enrichi.

Obsidia est un système d’exploitation cognitif gouverné dans lequel :
- plusieurs couches peuvent comprendre, explorer, mémoriser, proposer, vérifier, apprendre, construire et exécuter ;
- chaque couche possède une responsabilité bornée ;
- les domaines traduisent le réel dans un langage contrôlé ;
- Sigma observe la cohérence globale et relance l’exploration ;
- Brody opère et synthétise sans devenir l’autorité ;
- Obsidure construit et étend le système sous preuve ;
- Lean démontre mais ne décide pas ;
- la mémoire conserve la continuité mais ne devient pas souveraine ;
- X‑108 reste l’unique frontière d’autorité.

La règle mère demeure :

Cognition → Intention → Decision → Action → Proof

Une capacité peut exister sans être autorisée.
Une proposition peut être intelligente sans être vraie.
Une preuve peut être valide sans devenir une décision.
Une mémoire peut être utile sans gouverner.
Une action n’existe réellement qu’après passage par la structure d’autorité.

La V0.1 n’est donc pas une façade posée devant les composants. Elle est le premier produit utilisable, le point d’entrée unique et la boucle de construction qui doit englober progressivement toute la stack.

Désignation de travail retenue dans ce rapport : Obsidia Terminal V0.1.
Aucun nouveau nom de produit définitif n’est inventé.

1. LA VISION HAUTE

1.1 Le problème traité

Les architectures d’IA actuelles concentrent généralement trop de fonctions dans le modèle :
- interprétation ;
- planification ;
- mémoire ;
- choix d’outil ;
- décision ;
- exécution ;
- justification après coup.

Cette concentration crée une confusion entre intelligence et autorité.

Obsidia sépare ces fonctions. Le modèle, l’agent ou l’outil redevient un organe. Il peut produire une hypothèse, une réponse ou un plan, mais il ne possède pas mécaniquement le droit de transformer cette production en action réelle.

La proposition centrale n’est donc pas seulement « rendre l’IA plus sûre ». Elle est structurelle :

L’intelligence est distribuée.
L’autorité est bornée.
La décision est prouvable.
L’action est traçable.
La continuité est mémorisable.
Le système reste rejouable et auditable.

1.2 Le kernel ne doit pas comprendre le monde

Le kernel X‑108 n’a pas besoin de connaître la banque, le trading, l’aviation, le GPS, le commerce ou le contexte humain dans toute leur richesse.

Les domaines doivent traduire le monde dans l’alphabet du kernel :
- faits reconnus ;
- inconnues ;
- contradictions ;
- niveaux de confiance ;
- risques ;
- provenance ;
- contraintes ;
- conditions d’autorisation.

X‑108 ne juge pas le monde directement. Il juge la structure qui lui est remise.

Cette séparation permet :
- d’étendre Obsidia à de nouveaux domaines sans réécrire l’autorité ;
- d’éviter qu’un modèle probabiliste devienne implicitement souverain ;
- de conserver un noyau petit, stable et vérifiable ;
- de remplacer ou améliorer les organes sans modifier la constitution.

1.3 La machination complète

La carte juste n’est pas :

Moteur / Brody / Domaines / Périphérie comme blocs indépendants.

La carte juste est une machination unifiée :

Produit / Terminal
→ compréhension et traduction
→ plan actif
→ résolution des capacités
→ organes cognitifs et outils
→ mémoire et contexte
→ domaines et périphéries
→ Sigma et couches de contrôle
→ gates
→ X‑108
→ action bornée
→ preuve, receipt, replay, freeze

Tout peut graviter autour du noyau.
Tout peut traduire, contextualiser, proposer, enrichir ou alerter.
La valeur d’autorité ne se déplace pas.

2. ARCHITECTURE DU KERNEL VERS LE PRODUIT

2.1 Niveau 0 — Constitution et invariants

Ce niveau fixe les règles impossibles à contourner :
- KX108_ONLY ;
- aucune décision souveraine par Sigma, Brody, Obsidure, Lean, mémoire ou domaine ;
- séparation proposition / preuve / autorisation / exécution ;
- interdiction des bypass silencieux ;
- receipts et replay ;
- actions irréversibles gouvernées ;
- HOLD / BLOCK / ACT selon le périmètre actif ;
- frontières explicites entre public, shadow, readonly et production.

2.2 Niveau 1 — X‑108, frontière d’autorité

X‑108 est le kernel de décision.

Il reçoit une structure déjà traduite, puis évalue notamment :
- contradictions ;
- inconnues ;
- confiance ;
- risques ;
- intégrité des conditions ;
- compatibilité avec les invariants ;
- possibilité d’autoriser, bloquer ou maintenir en attente.

X‑108 ne remplace ni la cognition ni l’expertise de domaine.
Il tranche la validité structurelle du passage à l’action.

Sorties attendues :
- décision canonique ;
- justification structurée ;
- enveloppe de décision ;
- hash / receipt ;
- possibilité de replay ;
- statut d’exécution borné.

2.3 Niveau 2 — Proof perimeter

Le périmètre de preuve rend le kernel inspectable et reproductible :
- Lean 4 pour les propriétés formelles ;
- TLA+ / TLC pour la vérification de modèles ;
- vérificateurs exécutables Python ;
- contrôles RFC3161 ;
- QA croisée ;
- runner public de bout en bout.

Ce périmètre public ne représente pas l’intégralité d’Obsidia. Il expose une preuve reproductible de la frontière d’autorité et de ses invariants.

2.4 Niveau 3 — Gates et contrôles pré-exécution

Les gates organisent le passage entre une capacité et son autorisation :
- détection des opérations sensibles ;
- règles de readonly ;
- vérification des ressources et permissions ;
- contrôle de portée ;
- obligation de preuve ;
- refus d’auto-act, auto-commit ou auto-push non autorisé ;
- émission de HOLD ou BLOCK quand la structure ne suffit pas.

La gate est ex ante : elle agit avant l’irréversible.

2.5 Niveau 4 — Sigma, moteur transversal

Sigma n’est pas le kernel.
Sigma ne décide pas.
Sigma n’est pas supprimé par la spécialisation de ses fonctions.

Sigma reste le moteur transversal de :
- cohérence ;
- introspection ;
- recherche ;
- comparaison de chemins ;
- détection d’anomalies ;
- lecture des signaux spécialisés ;
- relance de l’exploration ;
- guidance post-Guard ;
- gel ou alerte lorsqu’un écart apparaît.

La réorganisation consiste à sortir de Sigma les lectures spécialisées qui méritent leur propre contrat, puis à laisser Sigma :
- les coordonner ;
- comparer leurs sorties ;
- repérer les incohérences inter-couches ;
- choisir où approfondir ;
- renvoyer une alerte structurée vers la chaîne gouvernée.

2.6 Niveau 5 — Peripheral Mesh

Le Peripheral Mesh regroupe les couches spécialisées qui observent une propriété précise.

Principe :
- chaque couche mesure ou traduit ;
- aucune ne devient souveraine ;
- leurs sorties sont bornées et auditables ;
- Sigma les agrège et les interroge ;
- X‑108 conserve l’autorité.

Familles retrouvées dans les traces :

A. OIE — Objective Invalidity Estimator
- estime le risque qu’une conclusion soit objectivement fausse ;
- détecte les mirages, erreurs plausibles et fausses convergences ;
- émet un score ou un signal ;
- n’annule jamais directement une décision du kernel.

B. Physical Signal Periphery
- lit des signaux physiques ou indirectement physiques ;
- couvre notamment réseau, système, Wi‑Fi, GPS, aviation et signaux terrain ;
- transforme le bruit, la friction ou les variations en éléments observables ;
- ne transforme pas un signal brut en vérité souveraine.

C. Causal Trace
- reconstruit les chaînes causales ;
- distingue corrélation, succession et dépendance ;
- permet de rejouer la formation d’une conclusion ou d’une action.

D. Provenance
- suit les sources, transformations et responsabilités ;
- conserve l’origine des données et des décisions intermédiaires ;
- permet l’audit d’intégrité.

E. Anti‑Mismatch
- détecte les décalages entre intention, représentation, plan, sortie et action ;
- empêche une réponse localement correcte de masquer une divergence globale.

F. Thermo / bruit / friction / cohérence
- lit l’entropie, la dissipation, l’instabilité et la température de cohérence ;
- transforme les perturbations en information sur l’état du système ;
- alimente Sigma sans remplacer le jugement du kernel.

G. Timeverse / OCS / cohérence temporelle
- suit l’ordre, la temporalité signée, la persistance et les changements d’état ;
- distingue événement, trace, état actif et héritage historique.

H. Moniteurs de domaine
- vérifient les contraintes propres à une arène ;
- restent bornés au contrat du domaine.

Important :
Les traces mentionnent un cadre canonique de douze couches, mais la liste exacte et définitive des douze noms n’est pas intégralement reconstructible depuis les éléments actuellement accessibles. Le présent rapport ne complète pas les noms manquants par invention. Les familles ci-dessus sont les blocs explicitement retrouvés ou déjà établis dans le projet. L’inventaire canonique des douze couches doit faire l’objet d’un freeze séparé.

2.7 Niveau 6 — Domaines et arènes spécialisées

Un domaine ne doit pas devenir un Brody miniature.

Il doit être :
- spécialisé ;
- borné ;
- lisible ;
- testable ;
- capable de traduire son réel ;
- connecté à l’agrégateur et au kernel ;
- incapable de contourner l’autorité.

Les domaines retrouvés comme déjà branchés, partiellement branchés ou audités sont :
- Bank ;
- Trading ;
- GPS ;
- AERO / Aviation ;
- Défense en bridge-only ou extension de signal ;
- e-commerce / entreprise comme trajectoire produit, hors périmètre P1 public.

La distinction importante :
GPS, Aviation, Défense et Wi‑Fi ne doivent pas être automatiquement transformés en couches souveraines indépendantes. Une partie de leurs fonctions appartient à Physical Signal Periphery ; une autre appartient aux adaptateurs ou arènes de domaine.

2.8 Niveau 7 — Mémoire / Graphiti

La mémoire maintient :
- continuité ;
- contexte ;
- provenance ;
- historique de projets ;
- liens entre décisions, preuves et artefacts ;
- reprise après interruption ;
- apprentissage durable.

Elle n’est pas souveraine.

Graphiti sert de support de continuité et de graphe mémoire.
Brody relie fortement cette mémoire au reste du système, mais Brody n’est pas « la mémoire ».

2.9 Niveau 8 — Brody

Brody est le pseudo‑LLM / LLM propriétaire et l’opérateur cognitif gouverné.

Rôles :
- comprendre et reformuler dans le langage du système ;
- synthétiser les sorties ;
- dialoguer avec l’utilisateur ;
- exploiter la mémoire ;
- construire une continuité cognitive ;
- raisonner avec les organes et domaines ;
- préparer des plans ou réponses bornées.

Non-rôles :
- décider à la place de X‑108 ;
- modifier la mémoire sans contrat ;
- autoriser une action irréversible ;
- absorber Sigma ;
- devenir le kernel.

La trajectoire Brody retrouvée dans les traces :
- fermeture de Brody V1 ;
- freeze local Brody V3 ;
- reconnexion réelle Brody + Graphiti + Terminal ;
- audit global Brody + domaines + connecteurs.

2.10 Niveau 9 — Obsidure

Obsidure est la couche de construction, proposition, extension et apprentissage sous contrôle.

Rôles :
- proposer des capacités ;
- générer ou modifier des composants bornés ;
- produire des propositions vérifiables ;
- transformer le travail réel en apprentissage de construction ;
- avancer par familles de propositions ;
- passer par Lean, les tests, les gates et X‑108 ;
- figer les capacités après preuve.

Doctrine :
Obsidure propose.
Lean prouve.
X‑108 décide.

Obsidure ne doit pas être présenté comme un agent autonome qui réécrit librement Obsidia. Dans la V0.1, il devient l’apprenti bâtisseur utilisé sur de vrais projets, avec chaque modification tracée, testée, réversible et gelable.

2.11 Niveau 10 — Terminal / ObsidiaShell / Workbench

Le Terminal devient le premier produit et l’interface unifiée de tout l’OS.

L’utilisateur ne doit pas lancer manuellement chaque couche.
Il formule une demande.
Le système détermine :
- ce qui peut être résolu localement ;
- quelle mémoire interroger ;
- quel domaine activer ;
- si Brody est nécessaire ;
- si Obsidure doit construire ;
- quelles gates doivent être traversées ;
- quelles preuves sont requises ;
- si X‑108 autorise la suite.

Le Terminal doit donc être à la fois :
- interface conversationnelle ;
- cockpit de preuves ;
- atelier de construction ;
- surface de statut ;
- routeur de capacités ;
- espace de reprise ;
- point de freeze ;
- produit utilisable.

3. SIGMA : RÉORGANISATION SANS DILUTION

3.1 Le malentendu à éviter

Dire que Sigma a été « découpé » peut laisser penser que son concept a perdu de la force.

Ce n’est pas la bonne lecture.

Avant la réorganisation, Sigma portait un grand ensemble de fonctions :
- cohérence ;
- observation ;
- anomalie ;
- causalité ;
- invalidité ;
- signaux physiques ;
- provenance ;
- temps ;
- bruit ;
- recherche ;
- relance.

La réorganisation a rendu ces fonctions explicites.

3.2 Ce qui a changé

Les fonctions spécialisées deviennent des couches ou modules contractuels :
- OIE mesure l’invalidité objective potentielle ;
- Physical Signal lit le terrain ;
- Causal Trace reconstruit les chaînes ;
- Provenance conserve l’origine ;
- Anti‑Mismatch compare les représentations ;
- Thermo lit l’instabilité ;
- Timeverse / OCS lit la cohérence temporelle.

3.3 Ce qui ne change pas

Sigma conserve :
- la vue transverse ;
- la comparaison inter-couches ;
- l’introspection ;
- la recherche ;
- la détection de rupture globale ;
- la relance de chemins ;
- le rôle de guide de cohérence ;
- la capacité d’alerter ou de geler en aval du Guard.

X‑108 conserve :
- l’autorité ;
- le passage final ;
- l’émission canonique ;
- la décision sur l’action.

3.4 Tableau de non-dilution

Fonction historique large
→ couche spécialisée
→ rôle conservé par Sigma
→ autorité finale

Invalidité / mirage
→ OIE
→ compare le score aux autres signaux et relance si nécessaire

Signal physique / bruit terrain
→ Physical Signal Periphery
→ contextualise et confronte aux autres couches
→ X‑108

Chaîne causale
→ Causal Trace
→ recherche les ruptures et incohérences
→ X‑108

Origine / responsabilité
→ Provenance
→ compare les traces et l’intégrité
→ X‑108

Décalage intention-sortie-action
→ Anti‑Mismatch
→ détecte la divergence globale
→ X‑108

Instabilité / dissipation
→ Thermo
→ lit l’état de cohérence du système
→ X‑108

Temps / ordre / persistance
→ Timeverse / OCS
→ détecte les contradictions temporelles
→ X‑108

Conclusion :
La spécialisation augmente la lisibilité et la preuve.
Sigma devient plus clairement transversal.
Le kernel reste inchangé dans son autorité.
Aucun concept n’est dilué.

Le projet démarre dans le chaos créatif, mais le fil reste constant : distribuer l’intelligence et empêcher la dérive de l’autorité.

La V0.1 est une interface de travail gouvernée capable de prendre une intention humaine et de la transformer en projet, artefact ou action bornée, tout en utilisant progressivement les couches d’Obsidia.

Elle doit être utile avant que toute la cathédrale soit terminée.

Elle ne masque pas les couches.
Elle les appelle selon le besoin.
Elle produit des preuves de ce qui s’est réellement passé.

- ne gouverne pas l’exécution.

6.5 Rôle d’Obsidure dans la V0.1

Obsidure :
- construit les capacités manquantes ;
- propose des modifications ;
- prépare tests et preuves ;
- apprend à partir des projets réels ;
- crée une boucle d’extension de la stack ;
- ne commit, ne pousse ou n’active rien hors gate.

6.6 Rôle de Sigma et du Peripheral Mesh

Sigma :
- vérifie la cohérence du projet en cours ;
- compare les couches ;
- repère les contradictions ;
- relance l’exploration ;
- expose les zones d’ombre.

Peripheral Mesh :
- apporte les lectures spécialisées nécessaires au contexte.

6.7 Rôle de X‑108

X‑108 :
- autorise le passage entre intention, décision et action ;
- conserve les invariants ;
- bloque les bypass ;
- produit la trace canonique.

6.8 Minimum produit réellement utile

La V0.1 doit fermer un flux vertical complet :

1. Une intention entre par le Terminal.
2. Le système retrouve le projet et son état.
3. Il forme un Active Plan.
4. Il résout les capacités disponibles.
5. Brody et/ou Obsidure travaillent.
6. Sigma et les couches nécessaires contrôlent.
7. Lean ou les tests apportent la preuve requise.
8. X‑108 tranche.
9. Une action bornée ou un artefact est produit.
10. La trace est enregistrée.
11. L’état est reprenable.
12. Le résultat peut être gelé ou annulé selon le contrat.

Critères de réussite :
- un vrai projet terminé de bout en bout ;
- aucune couche souveraine cachée ;
- audit complet ;
- reprise de session ;
- rollback ou freeze ;
- un domaine réel ;
- deux domaines supplémentaires en shadow ou simulation ;
- benchmark par ablation montrant la valeur de chaque étage.

6.9 Ce que la V0.1 n’est pas

La V0.1 n’est pas :
- l’AGI finale ;
- tous les domaines en production ;
- un agent libre d’agir ;
- une interface qui dissimule les preuves ;
- un remplacement de X‑108 par Brody ;
- une promesse d’autonomie totale ;
- une fusion de Sigma dans le kernel ;
- une dilution du Peripheral Mesh.
