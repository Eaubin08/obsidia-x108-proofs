# RFC3161 in P1

## Purpose

This document explains how RFC3161 is treated inside the public P1 perimeter.

## Layer 1: local tooling

The public P1 perimeter checks local tooling relevant to RFC3161, including:
- `openssl`
- local command availability such as `openssl ts`

This validates the local tooling layer.

## Layer 2: public RFC3161 anchor schema

The public repository includes schema-level validation for the public RFC3161 anchor artifact.

This validates:
- required fields
- hash algorithm
- merkle root format
- serial number format
- base64 presence
- public schema consistency

It does not by itself validate long-term availability of a third-party TSA provider.

## Layer 3: TSA network reachability

The public QA layer also probes external TSA endpoints.

Current public behavior:
- attempt `HEAD`
- if needed, fallback to `GET`

This reduces false negatives on endpoints that do not answer `HEAD` consistently.

## Reading TSA results correctly

Example reading:
- `4/4 TSA joignables` means all configured public endpoints were reachable in the validated environment at validation time
- this is a public QA result
- it is not a sovereignty claim over those providers

## What RFC3161 public P1 proves

P1 proves that:
- local RFC3161-related tooling is available in the validated environment
- the public RFC3161 anchor schema checks pass
- the public TSA probing logic works in the validated environment

## What RFC3161 public P1 does not prove

P1 does not prove:
- permanent availability of all TSA providers
- control over third-party TSA infrastructure
- full proprietary production timestamping infrastructure publication
